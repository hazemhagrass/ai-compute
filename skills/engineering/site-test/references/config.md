# site-test.config.json

The one file that adapts this skill to a specific site. Keep it in the project
repo, not in the skill.

## Shape

```json
{
  "base_url_prod": "https://example.com",
  "base_url_staging": "https://staging.example.com",
  "known_routes": ["/", "/pricing", "/apply"],
  "excluded_routes": ["/admin", "/portal/*"],
  "roles": ["guest", "customer", "admin"],
  "profile_dir": "~/.cache/site-test/profiles",
  "scenarios": [
    {
      "name": "pricing calculator updates on qty change",
      "role": "guest",
      "route": "/pricing",
      "writes": false,
      "steps": [
        { "click": "input#qty", "type": "3" },
        { "waitFor": "[data-price]" },
        { "assert": "[data-price]", "text": "$5,400" }
      ]
    }
  ]
}
```

## Fields

`base_url_prod` and `base_url_staging`: URLs, no trailing slash. The
`--base=` flag overrides both. Prod is read-only by default.

`known_routes`: canonical list the crawler always visits, even if the sitemap
is missing.

`excluded_routes`: paths the crawler must skip. Supports simple `*` suffixes.
Every entry needs a reason as a JSON comment or a companion doc; a run
declares the reason in `report.md`.

`roles`: the roles the harness knows about. `guest` is required and runs
first because it needs no sign-in.

`profile_dir`: where per-role Chrome profiles live. Persistent across runs so
OAuth/passkey sessions survive. Tilde is expanded.

`scenarios`: what the journey pass runs. Each has:

- `name`: shown in report and diffs. Stable across runs.
- `role`: must be in `roles`.
- `route`: the path the scenario starts on.
- `writes`: `true` for anything that would POST/PUT/PATCH/DELETE. Skipped
  unless `ALLOW_WRITES=1` and `--base=<staging>`.
- `steps`: an array of actions. Each is one of:

  ```
  { "click":   "css-selector" }
  { "type":    "css-selector", "text": "..." }
  { "waitFor": "css-selector" }
  { "assert":  "css-selector", "text": "..." }
  { "assert":  "css-selector", "attribute": "aria-expanded", "value": "true" }
  ```

## Adding a role

Add the role to `roles`. Add at least one scenario using it. On the next run
the harness will:

1. Open a browser window at the login page.
2. Print an attention banner in the terminal, naming the role.
3. Wait at a readline for a `Y` or `N` from stdin.

You sign in, press Y, the profile is saved, and the run continues.

## The two failure modes this config causes

Bad: putting site secrets here. Passwords, tokens, API keys never live in this
file. Use env vars.

Bad: pinning selectors to non-semantic classes generated by CSS-in-JS. When
the class rotates, the scenario "false-greens" against a fallback. Prefer
`data-*` attributes on the site, `aria-label`, or role selectors.
